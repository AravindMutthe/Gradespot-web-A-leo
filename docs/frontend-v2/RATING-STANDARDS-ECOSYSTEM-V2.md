## 2. The one finding that limits the re-rating: DB rows override local data

Course pages are SSG, and `src/lib/data.ts` prefers Supabase rows over local data at build time. A normal local build therefore still renders the OLD CCNA content from the live Supabase `courses` row, even though `src/data/courses.ts` is fixed. This was proven, not assumed: a rebuild with an unreachable Supabase URL (local fallback) renders the clean CCNA page; a normal build renders the old row. **Consequence:** the CCNA clean-up — and, by the same mechanism, any future local content fix — is NOT live-effective until the Supabase row is updated through an approved channel. That live write was deliberately NOT done in this branch-only pass. DB-vs-local reconciliation is now a pre-merge gate (§5a), and the same check should be run for every full course before merge, not just CCNA.

A related smoke-test honesty note: the first local smoke server picked up `.env.local` despite empty env vars being passed (Next's dotenv fills unset values), so its API tests ran against the live-configured server. The valid test payloads returned 202 (log path, not 201) and the server log shows the log-path line with no insert-error lines — consistent with no insert being attempted — but that run was not the clean isolated test intended. The bot/rate-limit results were re-verified in code and unit tests, and the 201/202 contract itself was verified in the earlier lead-fix pass; a fully isolated API re-test (bogus Supabase URL or a preview with its own env) is still owed before the lead fix is claimed verified end-to-end on a preview.

## 4. Ecosystem — one primary recommendation (unchanged, strengthened)

**Stay on the locked ecosystem and deepen it; do not replace it.** The fix pass strengthens the case: the new seam, limiter and bot checks were all built with zero new dependencies and zero paid services, inside the existing stack.

- **Frontend/hosting:** Next.js 16 on Vercel, bom1 (Mumbai) — close to Supabase ap-south-1 for latency + data residency, free tier, previews. Keep API-upload deploys until a git-linked pipeline is explicitly approved.
- **Backend/database:** Supabase Postgres, ap-south-1, shared Leo + replica today; Axon owns writes/business logic via typed API contracts as it matures — and the new site-settings seam is exactly the shape of that future contract (public values only, never secrets). The NestJS question is where logic lives, not abandoning Postgres — settle it by contract, not migration. **New consequence of §2:** whoever owns the `courses` table content owns the public curriculum — DB content governance (who may edit a row, with what review) must be settled before merge, not after.
- **Automation:** n8n self-hosted on the free Oracle VM + Meta WhatsApp Cloud API only (official API = no ban risk, the flagship's selling point).
- **Email/alerts:** Brevo free tier + WhatsApp Cloud API.
- **Analytics:** cookieless only — the CSP already forbids third-party trackers, and this is the only CWV/RUM route that does not break the privacy story.
- **Payments (future only):** Razorpay, one-time links + recurring, at SaaS stage only, per-transaction, no setup fee. Until then, services cash runs on the recorded off-site UPI rule (50% advance, balance in 48 hours), not through the website.
- **AI:** authenticated, rate-limited gateway + model-provider adapter, free-tier model first (Gemini free tier, Groq fallback in the record), grounded retrieval over the verified catalogue only, no browser keys, no model-authorized purchases/scores/lab access, no protected premium content to unenrolled visitors. The new rate limiter is the pattern that gateway must reuse — but with a shared store, not per-instance memory.

**Explicitly avoid:** shared-code monorepo including the `gradespot-official` umbrella (already rejected by the owner 2026-10-25 — breaks the no-shared-code contract, the Leo/replica design wall, and the stack lock; contracts + versioned API clients only); a second full UI library on public pages (Carbon belongs on admin/CRM/portal after compatibility testing); hotlinked assets, remote fonts/scripts, third-party trackers; Django/Firebase/Stripe rewrites (each contradicts a settled decision); unofficial WhatsApp gateways; paid SaaS/analytics/AI tiers before recurring revenue covers them; mixing the portfolio / GradeSpot-Axon / Royal Salon walls (repos, Vercel, Supabase, naming all separate); and — new from this pass — **editing DB content without a review trail**, now that DB rows are proven to override local data at build time.

## 5. Business model + entities (unchanged from the first rating)

**Model, in order (from FOUNDATION + REVENUE-STRATEGY):** (1) Brochure → lead platform, now — the site as a sales/service-delivery platform, revenue via the proven flow Website/QR/Ads → Lead → CRM → Automation → WhatsApp/Email → Counsellor → Admission. (2) Services projects + training enrollments as the cash engines, converting satisfied project clients into maintenance retainers. (3) Managed services (maintenance, cloud management, support, corporate retainers) as the stability engine — first financial goal: recurring revenue covering infrastructure + operating costs. (4) Digital products → SaaS only after dogfood + proof on GradeSpot (Pilot Customer #1), then sold to other institutes; SaaS subscriptions are explicitly "Future", not a current product. **Stay draft-only/unpriced until separately approved:** payments, any published price (revenue-table ranges **and** Set A vs Set B — both undecided; do not publish or quote the suggested ranges, and do not publish the revenue document's traffic/client/student figures, which are suggested/**UNVERIFIED** planning figures), institute-tier amounts, SaaS amounts, affiliate/reseller claims, AdSense (ranked Low, traffic-dependent, needs original policy-compliant content + approval), and any signed agreement through a form. Do not chase advertising as a primary engine.

**Entities — general information only, NOT legal/tax/CA advice.** Nothing here asserts GradeSpot's current legal entity, CIN, GST, or ownership. The published legal name "GradeSpot IT Solutions Pvt. Ltd.", the recorded 40/60 split (Aravind 40%, MD 60%), and the ₹30,000 runway are **recorded claims/TODOs, not verified facts** — the owner must confirm entity status, CIN, registered office, GST, and ownership with a lawyer/CA and the MCA record before any public claim; if the published name is wrong, correcting it is a legal disclosure fix, not a rebrand. This pass adds one practical entity-adjacent point: whichever entity is confirmed must also be the entity that owns and governs the Supabase content (courses, leads, certificates) and the future Axon settings row, because that content is now proven to be the public site at build time.

Why it matters: liability differs across student refunds, client delivery, and SaaS data incidents; IP (logo, course content, site code, Axon code, lead/certificate data) currently sits in personal repos and a phone folder with no written owner — whichever entity owns it must license it to the other; under DPDP/GDPR someone must be data fiduciary/controller for student/client data and someone must be processor when Axon serves other institutes; training fees, service fees, retainers, and SaaS subscriptions have different GST/invoicing/revenue-recognition treatments.

Forms to evaluate: **Private limited company** (limited liability, separate person, clearest for B2B contracts/hiring/future investment, heavier compliance) — evaluate as the GradeSpot operating company **if** the Pvt. Ltd. name is confirmed, and as a candidate for a separate Axon company later; **LLP** (limited liability, lighter compliance, less familiar to some enterprise buyers/investors); **partnership/proprietorship** (simplest, personal liability, poor fit once B2B contracts, fees at scale, or SaaS data responsibility are involved — evaluate only to rule it out).

**One vs two entities — recommended evaluation path:** keep **one** contracting entity for training + services through the lead-platform phase (do not create a second entity on paper before it earns it); prepare the two-entity split as a trigger-based plan — trigger it at the first paying third-party Axon institute, or external money, or third-party student data at scale, whichever comes first. At that trigger, IP assignment, a pilot-to-commercial licence, and a data-processing agreement must already be drafted. Founder terms to settle in writing before then: confirmed shareholding/profit share, who can sign contracts and open bank/payment accounts, brand/domain ownership, exit terms, and how GradeSpot-as-customer is charged for Axon once separate. **What would change this:** external investment, a large contract requiring a specific entity form/insurance, a tax/GST ruling changing training vs SaaS vs services treatment, or a verified finding that the current entity is not what is published — in which case correcting the public record outranks everything else.
